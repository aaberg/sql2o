# sql2o-bytecode

A `ResultSetHandlerFactory` for [sql2o](../../README.md) that builds a POJO or a record out of a row by generated bytecode
instead of by reflection.

```xml
<dependency>
    <groupId>org.sql2o.extensions</groupId>
    <artifactId>sql2o-bytecode</artifactId>
    <version>1.9.0-SNAPSHOT</version>
</dependency>
```

```java
Query query = connection.createQuery("select id, name from person");
query.setResultSetHandlerFactoryBuilder(new BytecodeResultSetHandlerFactoryBuilder());
List<Person> people = query.executeAndFetch(Person.class);
```

A factory can also be built and handed over directly, which is what the tests here do:

```java
BytecodeResultSetHandlerFactoryBuilder builder = new BytecodeResultSetHandlerFactoryBuilder();
builder.setQuirks(sql2o.getQuirks());

List<Person> people = connection.createQuery("select id, name from person")
        .executeAndFetch(builder.newFactory(Person.class));
```

Records work the same way, through the canonical constructor:

```java
public record Person(long id, String name) {}

query.setResultSetHandlerFactoryBuilder(new BytecodeResultSetHandlerFactoryBuilder());
List<Person> people = query.executeAndFetch(Person.class);
```

To find out where the bytecode is not being used, turn the fallback off. Every refusal then raises a
`Sql2oException` naming the reason instead of quietly mapping the reflective way:

```java
BytecodeResultSetHandlerFactoryBuilder builder = new BytecodeResultSetHandlerFactoryBuilder();
builder.setQuirks(sql2o.getQuirks());
builder.setFallbackAllowed(false);
query.setResultSetHandlerFactoryBuilder(builder);
```

**Not picked up by itself.** Nothing in core knows this extension exists, which is deliberate: it puts an ASM on the
runtime of every project that uses it, and that is not a decision to make on someone's behalf.

## What it actually removes

Per row, the reflective path of core asks for the metadata of the class (a cache lookup), constructs the object
(`Constructor.newInstance`), and for each column derives a name from the label, looks the property up in a map, and then
calls a setter or writes a field reflectively — each of those building an arguments array for the call.

A reader resolves all of that once, when the shape of the result set is first seen:

- which column goes to which member, and whether the member is a setter or a field;
- the type of that member, which is what the converter is chosen by;
- whether the column is wanted at all, or is compiled away;
- the name and description a conversion failure is reported against.

What is left per row is reading the column through the quirks, converting it and putting it somewhere. The readers are
verified against `CheckClassAdapter` before they are defined, so a reader that would not load fails in a test that names
the fixture rather than on the first query in production.

## What is compiled in, and what is not

The generated class is stateless — the object it builds lives in a local variable — so one instance is shared by every
query of the same shape and by every thread. Two things are therefore handed to it per call instead:

- **the quirks**, because `OracleQuirks` replaces the timestamps oracle hands out and `PostgresQuirks` asks for an
  `OffsetTime` where the column carries a zone. A reader that called `ResultSet.getObject` directly would map those
  columns wrongly and say nothing about having done so;
- **the converters**, because they come from the quirks. Resolving them per result set is what lets one compiled reader
  serve every `Sql2o`, and what makes a converter registered after compilation still be used.

Conversion itself stays in the `Converter` api, called from the generated code. A converter may do anything at all, and
keeping one implementation of "what does this column mean" is worth more than the handful of calls it costs.

## Where the bytecode can and cannot reach

A reader is defined into the package of the class it reads, through
`MethodHandles.privateLookupIn(targetClass, MethodHandles.lookup()).defineClass(bytes)`. That makes it the same runtime
package as the class, so **package-private and protected members are reachable without anybody passing `--add-opens`**.

**A private member is not.** This is a limit of the jvm and not a choice made here: private access is granted to nestmates,
and the jvm requires the class being reached to list the reader among its nest members — a list fixed in the bytes of a
class that was loaded long before this ran. Declaring the reader a nest host on its own is refused with
`current type is not listed as a nest member`. The reflective path has no such limit because it goes through
`setAccessible`, so a POJO whose fields are private is not slower here: it is simply not compiled, and is mapped the
reflective way instead.

The same applies to a private no-argument constructor.

## Refusals, and finding them

A shape a reader cannot produce exactly what the reflective path would is refused, and the whole result set goes to the
handler of core. Nothing is half-mapped. Refused are:

| | why |
| --- | --- |
| a private field or setter | unreachable from generated code, see above |
| a private no-argument constructor | the same |
| a property with neither a setter nor a field | there is nothing to write through |
| a dotted column name, `a.b` | a reader does not walk into a nested object |
| a class in the default package | no package to define a reader into |
| a class whose package cannot be defined into | a named module that does not open it |
| a name already taken by something else | two shapes sharing a digest, which is not guessed at |

`setFallbackAllowed(false)` turns the first of those into a `Sql2oException` naming the reason. It is the only way to find
out where the bytecode is not being used, which is the point of it.

## Known differences from the reflective path

Two, both pinned by tests, both about a value that is of the wrong type rather than about ordinary mapping:

- **A cast fails as a `ClassCastException`, not as the `IllegalArgumentException` of `Field.set`.** The wording of
  `Field.set` cannot be produced from generated code without a check per column on the way in. Both paths refuse the row;
  only the message differs. `ReaderParityTest` asserts that they differ rather than papering over it.
- **A `null` for a primitive component of a record raises `IllegalArgumentException("argument type mismatch")`**, which is
  what `Constructor.newInstance` says. That one is reproduced deliberately rather than left to a `NullPointerException`
  from unboxing.

Everything else is asserted to be identical, messages included: `ReaderParityTest` runs a matrix of shapes — primitives,
text, setters, inherited fields, enums, records, a row of nulls, an unmapped column, and a converter that refuses — through
both paths and compares the rows and the wording of the failures.

## The cache, and what it forgets

A shape is the target class, the column names, the naming convention, the column mappings, and whether an unmapped column
is an error. **The quirks are not part of it**, since they are consulted per call, so one entry serves every `Sql2o`.

Entries are held softly. A reader is defined into the class loader of the class it reads, so a strong reference from the
cache would keep that loader, and everything it loaded, alive. Losing an entry costs a recompilation and nothing else:
the next query of that shape finds the class already defined and takes it back rather than defining a second one.
`ReaderCache.clear()` forgets every shape, and `ReaderCache.size()` says how many are held.

The name of a reader carries a digest of the shape, class and columns and settings alike, which is why two classes in one
package with the same columns get readers of their own. That is worth a test of its own: without the class in the digest,
the second definition collides with the first and the reader already defined — built for the other class — would be handed
out for this one, which reads as values landing in the wrong fields rather than as an error.

## Benchmark

`org.sql2o.bytecode.bench.MappingBenchmark` (test sources, so surefire ignores it) reads 20000 `Employee`
rows — eight heterogeneous fields: strings, a `LocalDate`, a `BigDecimal`, an enum — through both paths and
compares time and allocation. There is no database in it: a hand-written `FakeResultSet` over a prebuilt
`Object[][]` hands out the same value types a driver would, so the converters do the same work they do on a
live base and what is measured is the mapping alone.

Methodology, without claiming JMH: both paths warmed up interleaved so the JIT heats both and the drift splits
evenly, every row consumed into a checksum, and the two checksums asserted equal — which also proves both paths
read the same thing. The bytecode side runs with the fallback off, so a quietly fallen-back measurement cannot
flatter the reflective path.

```
mvn -B -pl extensions/bytecode -am test-compile
java -cp "extensions/bytecode/target/test-classes;extensions/bytecode/target/classes;core/target/classes;..." \
    org.sql2o.bytecode.bench.MappingBenchmark
```

Pure mapping, per row (stable across runs):

| | ns/row | allocated/row |
| --- | --- | --- |
| pojo, bytecode | ~54 | 72 bytes |
| pojo, reflective | ~98 | 72 bytes |
| record, bytecode | ~50 | 72 bytes |
| record, reflective | ~77 | 120 bytes |

The 72 bytes on the POJO paths are exactly the result values — an `Employee` (48) plus a `LocalDate` (24) —
so neither path puts any GC pressure of its own: no varargs arrays, no holders, no name strings per row. The
record paths add one `Object[]` for the canonical-constructor arguments (48 bytes), which is what the
reflective `RecordBuilder` pays per row as well, on top of the record itself. A JFR profile of the run breaks
the reflective POJO 98 ns down to ~45% converters (shared with the bytecode path by design), ~35% assignment
through the `VarHandle`, and 8% `Constructor.newInstance`.

End to end against H2 the gap shrinks to ~1.1x (about 360 vs 400 ns/row), because both paths then share the
same ~300 ns of driver and converter work. The ratio, not the absolute number, is the signal here — and the
absolute numbers are machine-dependent hand measurements, not JMH.

## Known gaps

- `LoaderAwareClassWriter.getCommonSuperClass` is not covered, and deliberately so: the readers generated here never merge
  two reference types at a branch, so asm never calls it. It is the backstop for the day one does, and the one thing that
  would break first if a reader were loaded by a container — the one in asm resolves a class through its own loader, which
  is right for the library and wrong for a POJO loaded by a plugin.
- The remaining uncovered lines are branches that cannot be reached from a test: a package a named module does not open,
  a class in the default package, a missing SHA-256, a reader name taken by something else, and slot pushes past the
  first 128 columns.
- A named module that does not open its package to this one is refused. A caller who wants bytecode in a modular
  application has to open the package of their POJOs; there is no way around that from here.
- A dotted column name is a refusal rather than a generated walk into a nested object.
- No `Unsafe`, no `MethodHandles.privateLookupIn` into someone else's package, and nothing that would need a jvm flag.

## Running the tests

```
mvn -pl extensions/bytecode -am test
```

Nothing needs to be running: the database is in memory and the driver is on the test classpath, as with the hsqldb and derby
extensions.
